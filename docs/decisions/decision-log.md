Two consequences: R1 drops, and the cost driver becomes **payload size** rather than event frequency (new risk R15), since a change inside an attribute rewrites the whole list and `subscribe_entities` diffing cannot reach inside an attribute value. | Raising the publish throttle substantially, or a future data source that does create per-aircraft entities. |
| D20 | 2026-08-27 | **The project is named `hatty`.** Server binary `hatty`; Pi-side launcher `hatty-connect`. | settled | Home Assistant + TTY. Short, typeable, and unclaimed in this niche — the prior-art survey found no naming collision. The two binaries are named apart because they run on different machines and do unrelated jobs; sharing a name would confuse a log or a systemd unit at the worst moment. `BRIEF.md` retains the original `ha-dashboard` placeholder and is left unedited as the historical handoff. | A collision surfacing on a package registry at publication time. **The two-binary split is provisional pending §8.** `-server`/`-client` was considered and rejected: the Pi-side wrapper is not a client (the client is ssh plus the terminal emulator; the wrapper only sets the console font and is optional), and suffixing the primary binary demotes the product name. If option C wins, revisit as `hattyd` + `hatty` — or `hatty-attach`, since attaching a renderer to shared state is literally what happens — following the mosh/sshd convention. If option A wins, the current names are already correct. |
| D19 | 2026-08-27 | **Build rather than adopt.** No existing tool is adequate. | settled | Survey found two purpose-built HA TUIs — `bhdr` (archived, 4 stars, an entity *browser* not a dashboard) and a 3-commit stub — plus `dashbrew`, a capable Go/Bubble Tea dashboard builder that is **polling-only** and cannot stream. Adapting dashbrew means adding a streaming source, a state cache and half the widget set to someone else's project: comparable work to building, with less control. | A maintained, event-driven HA TUI appearing. Also: if Phase 2 chooses the screenshot-server approach (O10), this decision is moot rather than wrong. |
| D18 | 2026-08-27 | **State diffs are merged into the cache, never used to replace it.** | settled | `subscribe_entities` change messages carry only altered fields under `+`, and *removed* attributes under `-`. A client that treats a `c` message as a whole state silently loses every attribute not in that update, and one that ignores `-` retains attributes HA has dropped. Both failures are silent and look like stale data. | Nothing. This follows from the wire format. |
