# Phase 5, round three — the table is the design

The polar scope is descoped (decision **D33**). This round treats "a great looking table" as
the actual design problem, which it is. References: gh-dash, k9s and lazygit — all three named
in the brief, and all three fundamentally list-and-panel applications rather than chart
applications.

Generated by [`render_v3.py`](render_v3.py); every line asserted at exactly 100 columns.

**Braille appears only in the trend chart, never in the table.** If spike S2 fails, the table
is unaffected — which is the main structural benefit of dropping the scope.

---

## What makes a terminal table good

Applied throughout below, and worth stating because it is the substance of the design:

- **Numerics right-aligned at consistent precision.** Distance always one decimal, altitude
  always comma-grouped. The eye compares columns, not values.
- **Whitespace separates columns, not box-drawing.** Vertical rules inside a table add ink
  without adding information. gh-dash gets this right; most terminal tables do not.
- **One sort column, marked.** Ambiguity about ordering makes a live table unreadable.
- **A selection cursor that works without colour** — `▸` in the gutter, so the design does not
  depend on a colour pass that has not happened yet.
- **Inline micro-visualisation only where it earns its width.** The `RANGE` bar uses half-block
  characters (`▌`) for double the precision at no extra cost.
- **Severity in a narrow glyph column**, not by shouting.

**Recommended.** Three reasons:

   `db_metadata`. A detail pane uses it; a table alone discards it.
3. **It makes drill-down navigation concrete**, which the brief asks for and which nothing
   else in the design has yet exercised.

## Recommendation

**Table 2 as the `radar` screen**, with the trend from Table 3 available as a toggle. Table 1
is what Table 2 degrades into when nothing is selected.

Note what this buys: the airspace screen no longer needs the Braille canvas, ring geometry,
bearing-to-cartesian projection, or aspect-ratio correction. It needs a good table widget and
a detail pane. That is a materially smaller and more reliable thing to build, and it removes
the design's dependency on spike S2.

## Known problem in these mockups

**The sort indicator collides with the vertical-speed arrows.** `DIST↑` in the header reads as
a direction glyph because `↑ ↓ →` appear beside altitude in every row. Options: mark the sort
column with colour or bold once the colour pass happens, use a visually distinct glyph, or
label the V/S column explicitly. Left unfixed deliberately — it is the kind of thing mockups
exist to surface, and the right fix depends on the colour pass.

## Still open

- **Colour.** Everything here is monochrome. Altitude bands, flag severity (MIL / LADD / PIA),
  receiver health and the battery warning all want colour semantics.
- **Alert treatment** — what `binary_sensor.airspace_alert_military_close` firing looks like.
  Note `RCH451` in these mockups is a military contact at 12.6 nm, which is exactly the
  condition that alert fires on, and nothing in the design reacts to it yet.
- **The `home` screen**, where the runchart language from round two belongs.
- **Responsive behaviour** below 100×30 (decision D26). The table's columns have an obvious
  drop order — flags, CPA, operator, speed — which makes this tractable.
