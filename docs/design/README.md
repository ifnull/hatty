# Phase 5 — Candidate Layouts

Three competing designs for the primary dashboard at **100×30** (decision D1). The brief is
explicit: *"Do not settle immediately on the first design."* These exist to be rejected.

Generated by [`render_mockups.py`](render_mockups.py), which renders to a fixed grid and
**asserts every line is exactly 100 columns**. Hand-drawn ASCII lies — it is far too easy to
write a column that does not actually fit. The generator caught two real width bugs while
these were being drawn, which is the argument for keeping it.

Deliberately **block elements only, no Braille** — spike S2 has not run, and a design that
works without Braille loses nothing if Braille turns out to be available (D22/D23).
Data shapes and magnitudes are taken from the real dashboards; see
[`airspace-entity-model.md`](../planning/airspace-entity-model.md).

not survive the medium change.

- **Roughly a third of the grid is dead space.** Weather and Interior run out of content

  does not grow.

This is exactly what the brief means by "a different medium with different strengths."

## The finding underneath all three

**The combined dashboard is unbalanced at any proportion.** Airspace generates far more data
than weather and interior combined, and no arrangement of one 100×30 screen serves both well.
Every layout above either starves the table or wastes a third of the grid.

Decision **D30** — one dashboard is one screen — makes this a solved problem rather than a
compromise: `hatty radar` gives the airspace data the whole grid, and `hatty home` does the
same for environment. Layout C then becomes the *radar* screen with its environment rail
demoted to a status strip, and `home` gets a layout designed for sparse data rather than
squeezed into a leftover column.

**Recommendation: build `radar` first as Layout C, and design `home` separately** rather than
continuing to force both onto one screen.

---

## Two problems these mockups exposed

**1. The aircraft glyph is a width hazard.** `✈` (U+2708) has ambiguous East Asian width and
many terminals render it double-width, especially with emoji presentation. That is risk R3
and the same class of problem that killed the country flags (D28). Substitute a
guaranteed-single-width marker — `▲`, `●` or `+`. **Add to spike S2's width test.**

**2. Ring density needs tuning.** Five rings of dotted circles in a 47×17 cell area is
visually noisy where rings converge near the centre. Options: fewer rings, a lighter ring
glyph, or drawing only cardinal ticks rather than complete circles. A Phase 5 refinement,
not a structural problem.

---

## What is still not designed

- **The `home` screen**, now that it is separate.
- **Responsive behaviour.** Nothing below 100×30 has been drawn. Decision D26 says panels
  declare collapse-or-reserve; which panels collapse first at 80×24 is undecided.
- **Colour.** These are monochrome. Colour semantics — the brief's "colour should communicate
  state rather than decorate" — is a separate pass.
- **Navigation and drill-down.** The glance→detail pattern from the Airspace dashboard
  (select a row, expand a record) has no design yet.
- **Alert treatment.** `binary_sensor.airspace_alert_military_close` firing should be
  impossible to miss; none of these show what that looks like.
